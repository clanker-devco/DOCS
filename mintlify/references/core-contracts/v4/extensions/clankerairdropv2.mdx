---
title: "ClankerAirdropV2"
---

The **ClankerAirdropV2** extension lets a deployer airdrop a portion of the token supply via a merkle root, with more admin controls than **ClankerAirdrop**.

## How to set up

At token deployment, the deployer supplies:

1. How much supply to allocate to the airdrop (max 90%).
2. How long to lock up the airdrop (minimum 1 day).
3. How long to vest the airdrop (can be zero).
4. The merkle root specifying the recipients and their token amounts (can be zero and set later).

The **ClankerAirdropV2** extension data has this form:

```solidity
struct AirdropExtensionData {
    address admin; // controller of the token's airdrop admin functions
    bytes32 merkleRoot; // the merkle root of the airdrop
    uint256 lockupDuration; // the duration of the lockup period
    uint256 vestingDuration; // the duration of the vesting period
}
```

### Merkle root format

The airdrop expects leaves in the ABI-encoded format `(address recipient, uint256 amount)`. The **OpenZeppelin** MerkleProof library verifies proofs against the merkle root, and a JavaScript package is available on [GitHub](https://github.com/OpenZeppelin/merkle-tree).

<Warning>
This extension doesn't verify on-chain that the merkle root's leaves add up to the total supply of the token. The deployer is responsible for making sure the merkle root is valid. If a recipient is granted tokens in multiple leaves, they can claim the maximum of the granted amounts.

</Warning>

## Admin capabilities

Admins can do two main things:

1. **Recover unclaimed tokens** two weeks after the airdrop's lockup and vesting periods have passed. For example, if an airdrop has a 7-day lockup and a 7-day vest, the admin can recover tokens 28 days after launch (7-day lockup + 7-day vest + 14-day protected claim window for users).
2. **Change the merkle root** for their token. Admins can do this:
   * At any time, if the root was initially set to zero and is still zero.
   * 1 day after the lockup period has ended, if no users have claimed their tokens.

### Admin-facing functions

Only a token's admin can call these functions:

```solidity
// admins can claim the remaining balance after the claim expiration
// interval has been reached
function adminClaim(address token, address recipient) external;

// update the merkle root of the airdrop by admin if the merkle root is
// zero or if the claim overwrite interval has passed without a claim
function updateMerkleRoot(address token, bytes32 newMerkleRoot) external;

// update the admin of the airdrop
function updateAdmin(address token, address newAdmin) external;
```

## How to claim

To claim tokens, the recipient must have a leaf in the merkle root. Anyone can call the `claim()` function to transfer tokens from the airdrop to the recipient's address.

Claiming starts after the token's lockup period ends, and the claimable amount grows over the optional vesting period. For example, if a deployer wants to lock the airdropped tokens for 30 days and have all tokens available 60 days after deployment, they would set the `lockupDuration` to 30 days and the `vestingDuration` to 30 days. At 45 days after deployment, half of the airdropped supply would be accessible.

### User-facing functions

```solidity
// callable by anyone, transfers the available tokens to the recipient
function claim(address token, address recipient, uint256 allocatedAmount, bytes32[] calldata proof) external;

// helper function to surface the amount available to claim for a user,
// assumes that there exists a proof for the allocated amount
function amountAvailableToClaim(address token, address recipient, uint256 allocatedAmount) external view returns (uint256);
```
